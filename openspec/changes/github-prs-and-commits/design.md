## Context

See proposal.md for motivation. What shapes the approach, as it stands on the `timeline-view` branch:

- **Each loader is a pure module plus a script.** `github.ts` maps `gh` JSON to `NodeInput`s (`mapGhRepoToNode`, `mapGhIssueToNode`, both through `normalizeOccurredAt`) and derives `mentions` edges (`extractIssueReferences` masks fenced and inline code and bare URLs, then matches `owner/repo#N` before same-repo `#N`; `deriveMentionEdges` resolves against a set of known external ids, case-insensitively on the slug, skipping what does not resolve, self-references, and duplicate pairs); `ingest-github.ts` discovers repositories (`gh repo list --limit 1000 --json nameWithOwner,issues`, keeping `issues.totalCount > 0`), fetches each (`gh repo view`, `gh issue list --state open --limit 2000`) under `Promise.all`, and writes one run: one `upsertNodes`, one `upsertEdges`, `closeIngestRun` with counts. `git-repo.ts` parses `git ls-files -s -z`, classifies and reads files, builds the tree, and `loadGitRepoTree` writes nodes then `child_of` edges inside one `db.transaction` after validating every node up front; `resolveGitRepoEdges` throws on an unresolvable parent because a path tree cannot have one; `ingest-git-repo.ts` parses `--key` and runs git with a 256 MiB stdout buffer. Neither test file runs `gh`; `git-repo.test.ts` builds fixtures with `mkdtemp` and no `git init`.
- **Identity.** `github` keys `repo` by `owner/name` and issues by `owner/name#N`; `git` keys the root by `<key>` and entries by `<key>:<path>`; `deriveRepoKey` turns the origin remote into `owner/name` unless `--key` overrides. `upsertNodes` returns `{ id, sourceSystem, externalId, action }` per row, which is how a loader links what it just wrote; nothing public resolves a pre-existing node by external id (`bd-wq4`).
- **Edges are open text, and one row per node on the timeline.** No validator or query enumerates edge types beyond `child_of` and `blocks`; the explorer colours edges by source system, not type. `getTimeline` shows each neighbour once, under its heaviest edge to the anchor (`DISTINCT ON (node_id) … weight DESC, edge_type, edge_id`), so weights decide which relation a row names when a node is joined to the anchor twice.
- **Merges fold in every read on this branch.** `getTimeline`, `getNeighbors`, `getSubtree`, and `resolveDefaultViews` probe the anchor's aliases and fold far endpoints through `merged_into`. `mergeNodes` sets the loser's pointer and collapses chains; it does not rewrite edge rows. The upsert's `ON CONFLICT DO UPDATE` sets type, title, content, hash, metadata, run, and `updated_at` — never `merged_into`.
- **`relationLabel(edgeType, direction)`** in `apps/web/src/lib/timelineRow.ts` (timeline-view group 3) is where a new edge type gets its words.

## Goals / Non-Goals

**Goals:**

- A repository's timeline, anchored on either of its two nodes once merged, interleaves issues, pull requests, and commits with no read-side change.
- A file's timeline is its commits; an issue's shows the pull request that closed it.
- Every new node fills `occurred_at` through the same normalizer, at the writer, as the existing ones.
- Cross-loader links are resolved through one public read, not raw SQL in a script.
- Nothing fatal that is a property of history rather than of the load: a deleted file, an unloaded issue, a non-slug key.

**Non-Goals:**

- Fetching PR files, reviews, or commits from GitHub. The git loader owns commits; PR file lists are a later slice.
- Rename detection in `git log`. `--name-only` reports the post-rename path; the pre-rename path has no node anyway.
- Any change to the explorer beyond two relation labels.

## Decisions

### 1. Pull requests are a third mapping in the GitHub loader, under the issue identity scheme

`github.ts` gains `GhPullRequest` (the fields `gh pr list --json` returns for `number,title,body,state,isDraft,mergedAt,closedAt,createdAt,updatedAt,author,headRefName,baseRefName,url,labels,closingIssuesReferences`), `PR_NODE_TYPE = "gh-pr"`, `CLOSES_EDGE_TYPE = "closes"` / `CLOSES_WEIGHT = 1.0`, and `mapGhPrToNode(slug, pr)`: external id `${slug}#${pr.number}`, title, body as content, metadata `{ state, isDraft, mergedAt, closedAt, createdAt, updatedAt, author, headRefName, baseRefName, url, labels }` in the issue mapping's casing, plus `occurred_at` from `createdAt` through `normalizeOccurredAt` with the same item label shape. `ingest-github.ts` fetches `gh pr list -R <slug> --state all --limit ${PRS_PER_REPO_LIMIT} --json …` beside the issue fetch inside the same per-repository `Promise.all`, widens `discoverRepoSlugs`'s predicate to `issues.totalCount > 0 || pullRequests.totalCount > 0` (adding `pullRequests` to the discovery `--json`), and writes PR nodes in the same `upsertNodes` call as repositories and issues. Edges: `belongs-to` PR → repository, built where the issue edges are; `closes` PR → each `closingIssuesReferences[].number` whose `${slug}#${number}` is among the ids this run wrote (a closed issue is not loaded, so most historical closes resolve to nothing and are skipped, per the spec); `mentions` through `deriveMentionEdges` with `IssueRefSource`s for issues and PRs alike and the known-id set covering both — no change to the function, only to its inputs.

*Why creation is the PR's moment.* `timeline-view` decision 2 placed every item at its creation so the key is uniform and an item never moves; a merged PR at its merge instant would move on merge and would sort a still-open PR by a different rule. The merge and close instants are in metadata for the per-node fan-out `timeline-view` deferred. *Rejected: `mergedAt ?? closedAt ?? createdAt`.* *Rejected: a separate `gh-pr` numbering scheme* — GitHub numbers issues and PRs from one sequence, so `owner/name#N` is already unique and `#N` in prose resolves to whichever exists; a second scheme would make the same reference resolve differently depending on the loader's own bookkeeping. *Rejected: a transaction around the loader's two writes.* `upsertNodes` opens its own; the write is idempotent, so an edge-step failure leaves nodes the next run re-links. The design says so rather than fixing what has not failed.

### 2. Commits are a second record kind in the git loader's batch

`ingest-git-repo.ts` gains `--commits <N>` (`--commits=<N>` too; a non-negative integer, `COMMITS_DEFAULT = 500`, `0` disables) parsed in the `--key` loop, and runs `git log -n <N> --name-only --format=<record>` when `N > 0`. The record format is `%x1e%H%x00%P%x00%aI%x00%cI%x00%an%x00%s%x00%b%x00`: a record separator opens each commit, seven NUL-separated fields follow, and the paths `--name-only` appends run until the next separator. `git-repo.ts` gains `parseGitLog(stdout): GitCommit[]` (pure; splits on `\x1e`, then the first seven fields on `\x00`, then the remainder into paths by newline, trimming the blank line git inserts; a merge commit lists no paths under `--name-only` and gets none), `COMMIT_NODE_TYPE = "commit"`, `TOUCHES_EDGE_TYPE = "touches"` / `TOUCHES_WEIGHT = 0.8`, `commitExternalId(key, sha)` = `${key}@${sha}`, and `buildCommitNodes(key, commits)`: title = subject, content = the full message (`%s` and `%b` joined by a blank line), metadata `{ sha, parents: string[], author, authored_at, committed_at, files_changed }`, `occurred_at` from `%cI` through `normalizeOccurredAt` (it carries a zone). `loadGitRepoTree(db, tree, { commits })` validates commit nodes with the tree's before the transaction opens, upserts them in the same chunked node write, and resolves three edge kinds from the upsert's returned ids: `belongs-to` commit → root, `touches` commit → each changed path that is a `file` row in this load (a path with no row — deleted since, or skipped as binary/generated/oversized — is counted under `skippedPaths`, not thrown, because history is allowed to name what the tree no longer holds), and `mentions` commit → each reference from `extractIssueReferences(message)` resolved through `getNodesByExternalId` against `github` when the key matches the `owner/name` slug shape (otherwise every reference is counted unresolved). The identity lookup runs inside the transaction before the edge write, on at most the distinct references of the batch. The run's summary reports commits loaded, `touches` written, paths skipped, and references unresolved, beside the file skip counts.

*Why the git loader and not the GitHub API.* Commits are git's data: available offline, for any remote or none, and the file nodes they touch are this loader's own rows in the same batch — the one-transaction, resolve-from-returned-ids shape needs no cross-source lookup for `touches`. *Rejected: author date as `occurred_at`.* A rebase rewrites the committer date and leaves the author date; the committer date is the moment the commit entered the history the timeline is showing, and the author date is kept beside it. *Rejected: `-m` for merge commits' files.* It attributes every file of the merged branch to the merge; the branch's own commits already touch them. *Rejected: rename detection.* The pre-rename path has no node.

### 3. One identity lookup, in `lookup.ts`, closes bd-wq4

`getNodesByExternalId(db, pairs)`: `MAX_EXTERNAL_ID_LOOKUPS = 500`; each pair's `sourceSystem` and `externalId` trimmed and non-empty (`InvalidLookupIdError` naming the pair's position before SQL); one statement over `unnest($1::text[], $2::text[])` joined to `nodes` on `(source_system, external_id)` — the unique key — projecting `COALESCE(merged_into, id)` as the canonical id and the canonical row's `node_type` through a second join, deduplicated on the pair; result `{ found: [{ sourceSystem, externalId, id, nodeType }], notFound: [{ sourceSystem, externalId }] }`. Exported from core; the commit loader is its first consumer.

*Rejected: resolving inside the git loader with raw SQL.* `bd-wq4` was filed precisely because the seed script had to; a second script doing it would settle the question the wrong way. *Rejected: a `getNodes` overload.* Different key, different not-found semantics, different callers.

### 4. The two repository nodes stay two; the dogfood merges them, and re-ingest keeps the merge

The GitHub loader's `repo` (`owner/name`) and the git loader's root (`<key>`) are the intended cross-system duplication the store's merge exists for. The dogfood merges the git root into the GitHub node (loser = git root) with `brain_merge`, and the repository's timeline anchored on either id shows issues, PRs, and commits because `getTimeline` probes the survivor and its aliases. After the merge, `pnpm ingest:repo` upserts the loser row by external id — the upsert never sets `merged_into`, so the pointer survives — and re-asserts `child_of`/`belongs-to` edges to the loser's id, which is what they already are (`mergeNodes` rewrites pointers, not edges); every read folds them. `pnpm ingest:github` updates the survivor as any other row. The code view keeps opening from the git root: `getSubtree` folds a merged root, and `resolveDefaultViews` folds the declaring node.

*Rejected: the git loader attaching commits to the `github` repository node.* Couples two loaders through an identity guess, and a checkout with no GitHub remote would anchor its commits nowhere. *Rejected: a loader-side merge.* Identity is a person's decision, attributed to their session.

### 5. Weights say what a timeline row names

A commit is joined to the repository by `belongs-to` (1.0) and to files by `touches` (0.8); a PR to the repository by `belongs-to` (1.0), to issues by `closes` (1.0) or `mentions` (0.8). `getTimeline` shows the heaviest edge *to the anchor*, so a commit on the repository's timeline reads `belongs-to`, on a file's `touches`; a PR on an issue's timeline reads `closes` when it closes it, `mentions` otherwise — and when it does both, `closes` wins by weight, which is the more specific claim. `relationLabel` gains `closes` ("closes" / "closed by") and `touches` ("touches" / "touched by") in the direction convention timeline-view group 3 chose.

### 6. Tests: pure parsing on literal input, one real `git init` for the load

`github.test.ts` gains `GhPullRequest` fixtures, `mapGhPrToNode`, `closes` derivation, and `deriveMentionEdges` with a mixed known-id set; `gh` itself stays uninvoked. `git-repo.test.ts` gains `parseGitLog` on a literal log (a normal commit with three paths, a merge commit with none, a body with blank lines, a subject with `#12`) and `buildCommitNodes`. `git-repo-load.test.ts` gains a db-backed load whose fixture is a real repository — `git init`, two commits, one deleting a file — under a unique key, the first test in this repository that runs git; it asserts the commit nodes, `belongs-to`, `touches` only to the surviving file, the skipped-path count, `mentions` to a `github` fixture node written under the same unique slug, and unchanged on re-run. `lookup.test.ts` gains the identity lookup's found/not-found/merged/malformed cases.

## Risks / Trade-offs

- **A full PR ingest is several thousand nodes across the account.** → Bounded per repository (`PRS_PER_REPO_LIMIT = 2000`, above the largest repository's few hundred), fetched in the existing per-repository `Promise.all`; bodies are under the 64 MiB buffer. The count is recorded in the dogfood.
- **`closingIssuesReferences` mostly names closed issues, which are not loaded.** → Skipped and, in the summary, counted; the day closed issues are loaded, the edges appear on the next run with no code change.
- **`--name-only` under-reports merge commits and renames.** → Stated in decision 2; the branch's commits carry the files.
- **A NUL in a commit body would split a record wrongly.** → Git forbids NUL in commit messages; `parseGitLog` counts fields and rejects a malformed record with the sha rather than misattributing.
- **The merged repository root is re-upserted by every git run.** → The upsert cannot clear `merged_into`; a test in `git-repo-load.test.ts` merges a fixture root and re-loads to prove the pointer survives.
- **`occurred_at` at creation puts a long-lived PR far from its merge.** → Deferred fan-out, as the proposal says; the merge instant is one metadata read away.

## Migration Plan

No schema change. `pnpm ingest:github` once (new PR nodes, updated discovery), `pnpm ingest:repo . --key <slug>` once (commits; a repository whose key was overridden to a non-slug gets no `mentions`). Rollback: revert the code; `gh-pr` and `commit` nodes are inert data with valid `occurred_at` that the timeline would keep listing, so a rollback that wants them gone deletes by node type under the two source systems.
