One task group, one bead. Group 1 is the schema and the store primitive — the tombstone exists and every read already honours it, with nothing yet able to set it from outside SQL; group 2 is the core write path, attributable and batch-first; group 3 is the MCP surface. Each group ends with `pnpm check` green. Core tests hit a real Postgres; scope fixtures by a unique external-id prefix per test, never a store-wide count (`bd memories test-no-run-opened-assertions`).

## 1. Schema: tombstone column, view predicate, revision trigger

- [ ] 1.1 One migration in `packages/db` adding `nodes.deleted_at timestamptz` (nullable) and `node_revisions.deleted_at timestamptz` (nullable), with the drizzle schema updated to match. Both nullable with no default: `NULL` means "not deleted", which makes the backfill of existing rows a no-op.
- [ ] 1.2 In the SAME migration, `CREATE OR REPLACE VIEW resolved_nodes` with `WHERE merged_into IS NULL AND deleted_at IS NULL`. Keep the existing thirteen columns in their existing order and do NOT add `deleted_at` to the projection (design.md decision 2: `CREATE OR REPLACE` can only append, and a row visible through the view is by definition not deleted, so the column would be a constant NULL). Splitting this from 1.1 into a second migration would leave a window where deleted nodes are still returned — same file, deliberately.
- [ ] 1.3 In the SAME migration, replace `nodes_record_revision()` so its `INSERT INTO node_revisions (...)` list carries `deleted_at`, and replace `nodes_record_revision_update_trigger` so its WHEN clause gains `OR (old.deleted_at IS DISTINCT FROM new.deleted_at)`. Both are frozen explicit lists, like the view — a miss here means a deletion records no revision, or a re-delete records a spurious one. `IS DISTINCT FROM` is what makes "deleting twice records nothing" fall out without an application-level guard.
- [ ] 1.4 Decide and implement what `nodes_merged_into_must_be_canonical` does when the merge target is deleted (design.md Risks). Refusing is the expected answer — a merge that redirects live nodes into an invisible one loses them — but it is a behaviour change to an existing trigger, so make it explicit rather than incidental.
- [ ] 1.5 Add `AND deleted_at IS NULL` to retrieval's direct seed scan over `nodes` (`packages/core/src/retrieval.ts`), the one documented exception to `resolved_nodes`. Then verify by reading — not by assuming — that the endpoint fold (`coalesce(merged_into, id)`) in retrieval, lookup, timeline, tree and `resolveDefaultViews` drops an edge whose endpoint resolves to a deleted node rather than returning a tombstoned row.
- [ ] 1.6 `pnpm db:migrate` against a scratch database, then assert directly in SQL: setting `deleted_at` removes the row from `resolved_nodes`, records exactly one revision, and a second identical update records none. `pnpm check` green.

## 2. Core: deleteNodes / restoreNodes

- [ ] 2.1 New module beside `nodes.ts` and `merge.ts` exporting `deleteNodes(run, ids)` and `restoreNodes(run, ids)`, batch-first, each taking an `IngestRunHandle` and stamping `ingest_run_id` on every row it touches — "no write to `nodes` happens outside an ingest run" is an existing invariant and deletion is not the exception (see `mergeNodes` for the shape). Both return which ids they actually changed versus which were already in the requested state, so a caller can tell a no-op from an effect. Export from `index.ts`; add errors to `errors.ts` shaped like the existing ones.
- [ ] 2.2 `upsertNodes` clears `deleted_at` when a write matches a tombstoned `(source_system, external_id)` (design.md decision 6). This is the one behaviour change to an existing write path — a loader re-encountering a deleted node revives it rather than skipping it or writing a duplicate. Make sure the revive is part of the same statement, not a read-then-write.
- [ ] 2.3 Tests against a real Postgres: a deleted node leaves search / `getNodes` / `listNodes` / `getNeighbors` / `getTimeline` / `getSubtree`; its prior revisions are intact and a deletion revision is appended; deleting twice is a no-op with no second revision; deleting without a run is refused; deleting a merge survivor works and the nodes redirecting to it become unreachable; an edge with a deleted endpoint stops being traversed and returns with its original type/provenance/weight on restore; a re-load revives with exactly one node for those identifiers.
- [ ] 2.4 Extend `getNodeHistory` to report `deleted_at` among the fields it computes as changed, so a deletion reads as a deletion in the history rather than as an unexplained revision.
- [ ] 2.5 `pnpm check` green.

## 3. MCP: brain_delete and brain_restore

- [ ] 3.1 `brain_delete` accepting either `ids` or the `listNodes` selection grammar plus a required `expectedCount`, refusing — and deleting nothing — when the selection does not match that count exactly, naming both numbers in the error (design.md decision 7). Reuse `resolveListNodesOptions` for the selection rather than writing a second validator; a predicate outside that grammar is refused by the existing validation, not by new code.
- [ ] 3.2 `brain_restore`, taking ids only. No selection form: restoring is not the dangerous direction, and a selection cannot name rows the view hides anyway.
- [ ] 3.3 Both tools gated by `BRAIN_READ_ONLY` — not advertised and refused if called — alongside the existing write/link/merge tools, and the read-only test extended to cover them.
- [ ] 3.4 Tool descriptions that say what the agent needs to decide: that deletion is not permanent against a loader that still sees the source, and that a view's filter is the right tool for keeping a type out of a view for good. An agent reaching for delete to de-clutter is the exact case that motivated this change, and it is usually the wrong tool for that.
- [ ] 3.5 `pnpm check` green. Then dogfood over MCP against the real store: delete a handful of nodes by id, confirm they leave `brain_search`/`brain_list`, restore them, confirm they come back with their edges. Do NOT dogfood the bulk selection path against the live store.
